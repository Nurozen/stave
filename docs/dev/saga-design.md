# Saga design — logical grouping of spaces

Status: design agreed in discussion 2026-07-27/28, ready for implementation planning.
Grounded in a six-agent behavior inspection at commit `30a6513` (key verified facts inlined
below; see also the codebase map (regenerated by `/deep-explore` into `artifacts/codemap/`)).

## Motivation

One space ≈ one ticket. Multiple related tickets — separate PRs in the same or different
repos that must merge in a specific sequence, or heavily related work — need a first-class
grouping. A **saga** binds related spaces into one body of work, told in merge order.

Physical nesting (spaces inside spaces) was inspected and rejected: parent archive
`os.Rename` strands child worktree registrations in shared bare repos (verified: the moved
child worktree dies on the *next* `git worktree prune` issued by any other space's
archive/destroy on that repo), parent destroy leaves stale registrations blocking branch
reuse, dirty gates / portal sync guards / marmot route rewrites / generated AGENTS.md are
all blind to children. **Sagas are logical: members are ordinary flat sibling spaces under
`agent-work/`; the saga itself is a space of `kind: saga` sitting beside them.**

## Verified foundations (inspection facts the design relies on)

- All spaces' editable branches for one repo live as `refs/heads/stave/<space>/<repo>` in
  the **shared bare repo**; cross-space visibility is free (`internal/git/git.go:104-117`).
- Stacking already works mechanically: `--base refs/heads/stave/<other>/<repo>` passes
  `normalizeRemoteRef` (`internal/space/service.go:1341-1347`) verbatim and
  `git worktree add --no-track -b … <startPoint>` succeeds; drift
  (`rev-list --left-right --count <Base>...HEAD`, `git.go:176-194`) then live-tracks the
  sibling branch. Verified empirically. Bare `stave/...` bases fail (get `origin/` prefixed).
- `AddOptions.StartPoint` vs `Base` already decouple checkout point from drift target
  (review flow precedent, `service.go:80-92, 610-613`).
- Manifest write ceiling: loads are version-permissive, saves refuse when on-disk version
  is newer (`internal/space/manifest.go:90-114`). Schema-1 rewrites by older binaries
  **silently drop unknown fields** (Save marshals the typed struct).
- `kind` is a free-form persisted string; `review` is the precedent for kind-gated summon
  behavior and embedded skill install (`internal/summon/summon.go:151-158`;
  `internal/cli/review.go:21-26, 255-261`).
- Exactly three single-level enumerations of agent-work exist (memory list
  `space/service.go:1214-1235`, portal list `portal/service.go:439-456`, agent LLM context
  `agent/context.go:30-71`); there is no `stave space list` command.
- Validation gap: status/sync/destroy/memory verbs skip `ValidateName` and accept raw
  relative paths as IDs today (`service.go:710, 753, 900, 990`) — a traversal hole.
- Stave never pushes and never deletes branches (grep-verified); the agent planner refuses
  forge mutations (`agent/tools.go:234`). `WorktreeAddExisting` silently adopts a stale
  leftover branch, ignoring the requested base (`service.go:615-624`).
- `gh` best-effort metadata with soft degradation is established practice
  (`internal/cli/review.go:336-344`).
- Shared memory across spaces already works: attach-existing den (`--use`), marmot routes
  are many-paths→one-den, exact-path keyed (`internal/memory/marmot.go:373-423`).
- Review composes InitSpace + AddRepo + memory + skill install + chdir + summon at the CLI
  layer (`internal/cli/review.go:178-270`) — the composition pattern for `saga create`.

## Design

### Model

- A saga is a space (`kind: saga`) at `agent-work/<saga-id>/` with **no editable
  worktrees** (reference worktrees allowed). It reuses InitSpace, spec copy, AGENTS.md,
  CLAUDE.md link, memory attach, summon, shell handoff.
- **Membership and ordering live solely in the saga's manifest** (single authority; no new
  member fields — member manifests are rewritten constantly and schema-1 rewrites drop
  unknown fields). The saga manifest is written at **version 2** so older binaries can read
  it but the write ceiling prevents them from saving it and stripping the members list.
- Same-repo stacking is concretely expressed in each member's existing per-repo `base`
  field (`refs/heads/stave/<other>/<repo>`); cross-repo sequencing exists only as `after`
  edges in the saga manifest (no git mechanism exists for it).
- Ordering is a per-member `after: [...]` DAG (usually a chain). Sagas do not nest.

### Command surface

```text
stave saga
├── create <saga-id>            # kind: saga space; --spec/-s, --memory, --reference/-r
│                               # --edit rejected
├── list                        # sagas + members + kinds (first listing command)
├── status <saga-id> [--json]   # per member: repos, dirty, drift vs recorded base,
│                               # base health (ok | owner archived | merged | missing), PRs
├── sync <saga-id>              # fetch each unique bare repo once; sync members;
│                               # refresh saga references; run merge detection
├── add <saga-id> <space-id> [--after <member>]...   # membership upsert (re-run = update edges)
├── remove <saga-id> <space-id> # membership only; space untouched
├── archive <saga-id> [--force] # fail-fast all-member dirty check; reverse-DAG member
│                               # archive; saga space last
└── destroy <saga-id> [--force] [--memory keep|destroy|contribute]

stave space create <id> --saga <saga-id> [--after <member>]...
stave space retarget <id> [--repo <name>] --base <ref>   # rewrites recorded Base only;
                                                         # never touches the worktree
```

- **`space:` base sugar**: `-e api:space:pay-1` / `--base space:pay-1` resolve to
  `refs/heads/stave/pay-1/api`; validation checks the branch exists in the shared bare
  repo (today refs are syntax-only) and warns when create would adopt a stale leftover
  branch (`BranchExists` is available).
- **`--after` stacking rule**: for each repo shared between the new member's edits and the
  target's edits, base defaults to the target's branch; explicit `-e repo:base` wins.
  Cross-repo `--after` records ordering only.
- **Merge awareness** (status/sync), layered and read-only: (1) git ancestry after fetch —
  member branch tip ancestor of `origin/<original base>` (catches merge-commit/FF; cannot
  catch squash/rebase merges); (2) `gh pr list --head <branch>` / `gh pr view` —
  authoritative regardless of merge strategy, soft-degrading like review metadata. PR
  *identity* (repo+number) may be cached in the saga manifest after discovery; merge
  *state* is always fetched live (manifests store identity, not state).
- **Guards**: archiving/destroying any space whose branch is a recorded base of another
  live space warns (refuses without `--force`); saga archive orders members by reverse
  DAG and checks all members' dirtiness up front. `stave summon <saga-id>` works as-is;
  `kind: saga` selects the saga prompt and auto-launches the embedded skill (`--prompt`
  overrides).
- **Precursor**: add `ValidateName` to the currently-unvalidated verbs (closes the
  traversal hole) with a dedicated path validator distinguishing "reject traversal" from
  any future multi-segment allowance.

### Manifest schema

Saga `.stave.yaml` (version 2; `saga` block additive):

```yaml
version: 2
id: checkout
kind: saga
createdAt: …
specPath: spec
repos: []            # reference-mode entries only
memories: […]        # saga-owned den; members share via attach-existing (unowned there)
saga:
  members:
    - id: pay-1
    - id: pay-2
      after: [pay-1]
    - id: pay-web
      after: [pay-2]
      prs:
        - repo: web
          number: 517   # identity only; never merge state
```

Validation: members exist, are not sagas, `after` targets are members, DAG acyclic,
IDs use the existing charset. **Member manifests: zero new fields** (stack lives in the
existing `base`; "which saga am I in" = one-level scan for `kind: saga` manifests).

### AGENTS.md and agent surface

- `kind: saga` gets its own `writeAgents` template: purpose, spec pointer, members in
  merge order with relative paths, branches and stack bases, "work inside member
  directories; their AGENTS.md governs edits", "run `stave saga status <id> --json` for
  live state", "never rebase/retarget without being asked". Static structure in the file;
  volatile state through the command. Regenerates on every saga-manifest write — which by
  construction includes every membership change.
- Member AGENTS.md gains a generated `## Saga` section (saga name, relative path, stacked
  base per repo, status command). Saga membership changes re-touch affected members'
  AGENTS.md via the saga service.
- Summon prompt for `kind: saga` mirrors the template; `saga create` installs an embedded
  `.claude/skills/stave-saga/` skill (pr-teach pattern) teaching the operating loop
  (status → interpret drift/base health → propose retarget/restack). AGENTS.md remains
  the cross-agent (Codex-native) baseline; the skill is Claude-only and additive.
- LLM planner (later phase): `stave_saga_create/status/add`, saga awareness in the context
  snapshot (currently a flat one-level scan), extend `plannedSpaces` so one plan can
  create-then-add, and accept the `space:` base sugar in tool refs.

### Out of scope (v1)

Forge mutations (push, PR create/retarget — stave has no push anywhere), rebasing
(stave records/measures; humans or summoned agents restack), nested sagas, saga-level
portals (a saga is an ordinary space to the portal subsystem; members are siblings so no
nesting hazards apply), MCP exposure.

### Phasing

1. **Bless stacking** (no schema): `space:` base sugar + base-existence validation +
   stale-branch warning + traversal-hole fix + documented stacking recipe.
2. **The saga record**: version-2 saga manifest, `saga create/list/status/sync/add/remove`,
   `--saga`/`--after`, saga + member AGENTS.md templates, saga summon prompt + embedded
   skill, merge detection in status/sync.
3. **Lifecycle + planner**: ordered archive/destroy with dependent guards, `space
   retarget`, PR identity caching, `stave_saga_*` tools + context + `plannedSpaces`
   extension.

### Open questions (planner should propose answers)

- Human-readable `saga status`: distinguish "merged (ancestry)" vs "merged (gh/squash)" in
  human output, or only in `--json`?
- `retarget` without `--repo`: apply to all stacked repos whose base merged (convenient)
  vs always require explicit `--repo` (safer)?
- After a squash-merge is detected, should status suggest archiving the merged member
  (its local branch is permanently divergent)? Suggested: yes, suggestion only.
- Exact `saga status --json` schema (must be a stable contract, like portal status).
